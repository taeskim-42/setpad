# 숫자 정확성 계약 — 2026-09-13, 2026-09-23 개정(기록 질문 contract 2)

모델이 해석한 숫자·기간·조건은 제안이다. 사용자에게 확정된 계산 결과로 보여주거나 운동 설정에 저장하기 전에 확인을 받는다. 직접 운동과 지표를 선택하는 경로는 저장된 완료 기록을 코드로 계산한다.

## 적용 경계

- 모델이 낸 질의(contract 2, `RecordQuery.decode`)는 모두 `requiresConfirmation`을 가진다. `runQuery`는 확인 전인 모델 질의에 답을 내지 않는다. 이름이 둘 이상일 때 칩으로 고른 비교는 사람이 고른 것이라 묻지 않는다.
- 확인 줄(`describeQuery`)에는 운동과 제외한 운동, 측정과 무게 단위, 연도를 포함한 시작·종료 날짜, 무게·횟수 조건(≥ > ≤ < = 기호 그대로), 요일, 메모 낱말, 마지막 N번, 묶음, 상위·하위 N, 합계·평균을 표시한다. 비교는 항목마다 한 줄로 보이고, 차이는 뒤 − 앞으로 적는다.
- 검색어를 바꾸면 확인이 해제된다. 캐시에는 해석만 보관한다. 같은 질문으로 돌아와도 다시 확인한다. 언어·표시 단위·날짜가 달라지면 이전 확인이 적용되지 않는다.
- 자연어 운동 설정은 원문과 편집 가능한 이름·무게·단위·총 목표 횟수·세트당 횟수·목표 세트 수를 먼저 보여준다. 확인 전에는 운동 블록이나 완료 세트를 만들지 않는다. 취소하면 원문이 남는다.
- 확인 중 숫자를 수정했다면 이전 숫자가 포함된 원문을 운동 제목으로 재사용하지 않는다.
- 메모·종합 질문도 질의로 바꿔 코드가 센다. 목록은 계산에 쓰인 원본 기록(evidence)을 보여준다. 앱의 검색 경로에서는 자유 서술 모델 답변을 생성하거나 표시하지 않는다. 근거 ID가 존재한다는 사실만으로 서술 속 숫자가 맞다고 볼 수 없기 때문이다.
- 현재 운동 설정은 일정·날짜·시간 목표를 표현하는 필드를 제공하지 않는다. 명확하게 감지한 일정·시간 문장은 일부 숫자만 적용하지 않고 입력 실패로 보존한다. 일정 관리 기능을 새로 추가한 것은 아니다.

## 확인한 계산 결함과 수정

- 사용자가 명시한 단일 기간은 모델이 다른 단일 기간을 반환했어도 우선 적용한다.
- 횟수 조건만 있는 문장에 모델이 붙인 무게 조건을 제거한다. 지원하지 않는 표현과 복합 의미까지 자동으로 확정하지는 않는다.
- 날짜 이동은 24시간 단위 빼기가 아닌 달력 날짜 연산으로 처리한다. 연말·윤년·서머타임 경계를 테스트한다.
- kg/lb 필터는 저장된 십진수 표현과 정확한 변환 비율 `1lb = 0.45359237kg`을 정수 분수로 비교한다. 경계값에 임의의 오차 허용치를 적용하지 않는다.
- 같은 단위의 원래 측정값은 저장 정밀도를 그대로 표시한다. 환산값·평균·차이·차트 축 등을 반올림할 때는 `≈`를 표시해 정확한 값과 구분한다.
- 문장형 운동 제목 대신 실제 운동 식별자 `block.exercise`로 집계한다.
- 합계·최고값·평균과 필터 판정에 필요한 측정값이 누락되면 일부 세트만으로 숫자를 만들지 않는다. 누락은 **운동 단위**로 본다(2026-09-23).
  - 그 종류의 값을 한 번도 적지 않은 운동은 그 측정의 대상이 아니다. 무게 측정에서 풀업·플랭크, 거리에서 벤치프레스가 그렇다. 빼고 계산하며, 뺀 이름을 각주(`queryOutOfScope`)에 적는다. 그래야 "이번 주 총 볼륨"이 맨몸 운동 하나 때문에 늘 빈칸이 되지 않는다.
  - 그 종류의 값을 적은 운동 안에 값이 빠진 세트가 있으면 그 칸은 비운다(—). 까닭은 각주(`queryMissingFor`)에 적는다.
  - 무게·횟수 조건이 걸린 필드를 어떤 세트만 가진 운동은 조건을 판정할 수 없다. 그 운동의 칸도 비운다.
  - 합계 줄은 모르는 칸이 하나라도 있으면 비운다. 셀 세트가 없는 칸은 합산형 측정(운동한 날·세트·횟수·볼륨·거리·시간)에서 0으로 센다.
- 추정 1RM은 Epley(w×(1+r/30), r=1이면 w)로 계산하고 1–10회 세트만 쓴다. 11회 이상 세트는 정의상 빼고, 횟수가 없는 세트는 누락으로 본다.
- "넘긴·넘게·초과·over"는 `>`, "이상·at least"는 `>=`로 읽는다. 규칙 층은 이상·이하만 글에서 직접 읽고, 초과·미만은 모델 몫이다.

## 평가 계약

`tool/question_grading.dart`는 모델 질의와 정답을 **같은 디코더**(`RecordQuery.decode`, 기준일 2026-09-09)로 푼 뒤 뜻 전체를 견준다. 날짜는 풀린 것으로, 생략한 키는 기본값을 채운 것으로 본다. 견주는 것은 종류와 까닭, 운동·제외, 시작·종료 날짜, 무게·횟수 조건과 단위, 요일, 메모, 마지막 N번, 측정(순서 포함), 묶음·정렬·개수·합계, 비교 항목이다. 정답에 없는 조건도 오류다.

- 운동, 요일, 범위 조건 둘은 집합으로 본다. 비교 항목은 순서대로 본다(앞이 기준). 메모는 정답 어간을 모두 담았으면 맞다.
- 정답은 대안을 여럿 둘 수 있고, 하나만 맞으면 된다. 뜻을 가르지 않는 키는 문항마다 `ignore`로 뺀다(예: "가장 오래 안 한 운동"의 개수).
- `tool/questions/v2.json`: 212문항. 한국어 44문항과 다른 일곱 언어 24문항씩이다. 범주는 운동 비교·기간 비교·순위·묶음·측정·조건·종합·거절 8개이고, 한국어는 범주마다 5개 이상, 다른 언어는 3개씩이다. 운동 이름은 각 언어의 `seedNames`에서 가져온다.
- dev·heldout(298문항씩)은 `v2Expected()`로 v1 정답을 v2 정답으로 바꿔 계속 채점한다. 두 운동 3건과 초과 2건은 v2 정답을 적어 이제 채점한다. "요즘 어때"는 기간 없음과 최근 28일을 둘 다 맞게 본다. 초성 두 글자 3건만 관찰로 남는다.
- 모델 없는 검사(`test/record_query_gate_test.dart`): 최악 출력 넷에 대한 게이트(dev·heldout 전수 일치)와, v2.json의 첫 정답을 모델 답으로 넣었을 때 규칙 층이 그것을 망치지 않는지를 본다. 알려진 예외는 1건이다. 베트남어 "nhìn chung"(전체적으로)의 chung이 퍼지로 Chùng Chân(런지)에 닿아 순위가 운동 하나로 접힌다.
- 실제 모델 평가: `DEEPSEEK_API_KEY=... flutter test --no-pub tool/remote_eval_test.dart`. 운영 한도를 쓰지 않도록 서버를 거치지 않고 DeepSeek를 직접 부른다. 설정은 운영(gymdojo `lib/model-json.ts`)과 같다: `deepseek-flash`, max_tokens 400, thinking 끔, `json_object`. 키가 없으면 건너뛴다.
  - 지표: 정확 일치율, 무효율(답은 왔으나 디코드 실패), 자신 있게 틀림(숫자를 보일 질의가 불일치), 거절(unsupported인데 불일치), 평균 토큰(usage). 그물·HTTP 실패는 채점에서 뺀다.
  - 외부 API 키와 비용(약 510문항)이 들어 사용자 승인 뒤에만 돌린다. 합격선도 사용자가 정한다. 제안은 한국어 정확 일치 90% 이상, 무효 2% 이하다.

기존 보고서의 95.6% 및 ‘자신 있게 틀림 1%’는 날짜·추가 조건을 누락한 구 채점기에 근거하므로 현재 정확도 근거로 사용하지 않는다. contract 2 이후 실제 모델 정확도를 새로 측정하지 않았다. 확인 요청의 증가를 해석 정확도 향상으로 계산하지 않는다.

이 계약은 모델 해석 자체의 오류율 0%나 모든 소프트웨어 오류의 부재를 증명하지 않는다. 사용자 확인도 의미 해석의 수학적 증명이 아니다. 새 자동 적용 경로는 별도로 검증해야 하며, 모델 신뢰도나 느슨한 벤치마크 점수만으로 이 확인 경계를 우회해서는 안 된다. 저장된 원본 데이터의 정확성과 평균·단위 변환의 표시 반올림도 모델 해석 정확도와 구분한다.
