# 로컬 질문 해석 검증 — 2026-09-09

기록 질문을 다른 모델로 보내지 않고 기존 기기 내 LLM을 사용한다. 질문은 짧은 의도(action, exercises, periods, 선택적 조건)로 받고, 앱이 이를 검증된 조회 명령으로 변환한다. 날짜 경계·단위 변환·집계·비교는 코드가 처리한다. 질문 문구를 정규식으로 분류하지 않는다. 기록을 읽어야 하는 자유 질문은 기존 근거 검색과 로컬 답변 생성 경로를 유지한다.

불필요한 오늘 날짜를 프롬프트에서 제거하고, 질문을 운동명 목록 뒤에 배치했다. 긴 출력 규격 대신 간결한 의도와 대응 예시를 사용한다. iOS의 강한 출력 형식 제한은 이 평가에서 정확도가 낮아 최종 변경에 포함하지 않았다.

## 실제 모델 결과

- 환경: iPhone 17 Pro 시뮬레이터, iOS 26.5, Foundation Models 사용 가능 상태, 한국어 질문.
- 최초 구현: 18개 중 7개 정확, 해석 중앙값 1,286ms.
- 최종 구현: 26개 중 20개 정확. 첫 요청 1,915ms, 중앙값 1,248ms, 90백분위 1,476ms.
- 별도 반복 질문 확인: 최초 해석 1,205ms, 동일 질문의 캐시 조회 113μs. 캐시는 의도만 보관하며 계산 결과나 메모 답변을 보관하지 않는다.
- 측정에는 모델 호출과 조회 명령 검증이 포함된다. 입력 디바운스 750ms, 화면 렌더링, 실제 기기의 발열·다른 앱 부하는 포함되지 않는다. 첫 요청 시간은 이번 실행의 첫 호출이며 모델이 완전히 내려간 상태의 콜드 스타트를 보장하지 않는다.
- 성공 기준은 운동명, 집계 방식, 기간, 필터 방향·값·단위, 비교/순위가 모두 일치하는 것이다. 단순히 JSON 생성에 성공했다고 통과시키지 않는다.
- 작은 개발용 평가 집합이다. 프롬프트 조정에 쓰인 질문과 추가 표현이 섞여 있고 반복 실행했으므로 전체 사용자 정확도나 독립적인 블라인드 평가로 해석하지 않는다. Android에서는 빌드를 확인했으며 실제 모델 정확도는 측정하지 않았다.

실행: `flutter run -d <device> -t tool/evaluate_record_query.dart`

평가 진입점은 빈 화면과 메모리 안의 운동명 목록만 사용한다. NotesStore를 만들거나 실제 기록을 읽고 쓰지 않는다. 최종 결과는 `artifacts/record-ai/evaluation/local-validation.json`, 초기 결과는 같은 디렉터리의 `baseline.log`에 있다.

## 속도와 표시

동일한 질문이 실행 중일 때 검색을 다시 눌러도 모델 호출을 취소하고 재시작하지 않는다. 검증된 의도는 메모리에 최대 32개 저장한다. 날짜·운동명 목록·표시 단위·언어가 바뀌면 별도 키로 다시 해석한다. 기록 값만 바뀐 경우 기존 의도로 최신 기록을 다시 계산한다. 근거를 읽는 자유 답변은 새로 생성한다.

답 카드에는 실제 적용한 기간과 ≥/≤/= 무게·횟수 조건을 표시한다. 이 표시는 해석을 확인할 단서이며 모델 오류가 해결됐다는 보장은 아니다.

## 후속 검토와 속도 개선 — 2026-09-09 저녁

이번 변경:

- 입력 디바운스를 750ms에서 300ms로 줄인다. 검색 제출은 즉시 실행한다.

## 코드가 먼저 정하는 것들 — 2026-09-09 밤

남은 실패 셋을 모델을 더 가르치는 대신 **코드가 먼저 처리하는** 쪽으로 풀었다. 모델은 여러 칸을 한 번에 채우면 칸마다의 오차가 곱해진다. 사람의 글자에 또렷이 적힌 것은 코드가 읽는 편이 정확하고 빠르다.

- **철자 정규화.** 질문을 보내기 전에 사전 키(별칭·다른 언어 이름)와 정확히 같은 낱말을 정식 이름으로 바꾼다. "스쾃 PR" → "스쿼트 PR". 퍼지는 쓰지 않는다 — 오타를 잘못 바꾸면 질문이 바뀐다. 스쾃은 사전 alias 에 넣었다(표기법이지 오타가 아니다).
- **디코더의 퍼지 대응.** 모델이 사용자 철자를 그대로 돌려줘도 목록에 없다고 버리지 않고 검색과 같은 퍼지로 한 번 맞춘다. 아무것도 안 닮은 이름은 여전히 버린다.
- **기간 낱말.** 의도에 기간이 없고 글에 기간 낱말이 **하나** 있으면 코드가 채운다(오늘·이번 주·지난달·올해·최근 N일…). 둘이면 비교 질문이라 모델에 맡긴다.
- **숫자 조건.** "80kg 이상 5회 이상" 처럼 글에 적힌 이상·이하 조건은 코드가 뽑고 모델보다 앞선다. 초과·미만은 무게 경계가 애매해 모델에 맡긴다. 단위도 글의 kg/파운드가 정한다.
- **PR.** "PR", "최고 기록", "개인 기록" 은 뜻이 하나다. 모델이 이걸 순위로 읽으면(실제로 "PR 얼마?" 를 운동일수 순위로 냈다) 운동이 하나 지목된 경우에 한해 heaviest 로 바로잡는다.

실제 iOS 시뮬레이터 평가(같은 38문항): **38/38** (직전 28/34 → 35/38 → 37/38 → 38/38). 중앙값 1,412ms, 90백분위 1,627ms, 첫 호출 3,227ms. 원본: `artifacts/record-ai/evaluation/code-first.log`.

**이 숫자도 믿지 마라.** 프롬프트와 코드를 고치는 데 쓴 바로 그 문항이다. 블라인드 평가가 아니고, 사용자 전체의 정확도도 아니다. 사용자가 실제로 치는 30문장으로 다시 재야 한다.

## 캐싱에 대해 — 실측

- 기록을 모델 컨텍스트에 넣는 것은 안 된다. 한계가 4,096 토큰이다(모델 오류 원문: "Content contains 5139 tokens, which exceeds the maximum allowed context size of 4096."). 1년치 617줄은 약 10,900 토큰이고, 100줄만 넣어도 응답이 4,266ms 로 지금의 3배 느려진다. 숫자를 모델에 주면 산수를 모델이 하게 되는 것도 문제다.
- 지시문 prewarm 은 첫 호출 벌금을 없앤다(macOS 실측: 803ms → 265ms, 정확도 동일). 이미 배선돼 있다.
- 세션 하나를 계속 재사용하면 속도는 같고 정확도가 15/15 → 10/15 로 떨어진다. 앞 질문이 뒤 답을 오염시킨다. 한 번 쓴 세션은 버리는 지금 방식이 맞다.

**남은 실패(held-out 25건)와 왜 두는가.** 오타 표기 + 의도 동시 실패 12 — 오타를 퍼지로 바꿔 보내는 것은 질문을 바꿀 수 있어 하지 않는다. 모델이 기간을 지어낸 것 9 — 글에 없는 것을 코드가 뺄 근거가 없다. 두 운동 3 — 비교·순위·합 중 무엇인지 글만으로 정하기 어렵다. 예외 1.
